# Engine 2, milestone E6 (app integration and the fighter guide) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Studio app fight, search, balance, preview, queue, render and record Engine 2 matchups next to
current-engine ones, with no mixed-engine matchups and the TEST DUMMY reachable only through a developer switch.
Write `docs/studio/engine2/FIGHTER-GUIDE.md`, the guide every fighter session (F1 to F40) follows.

**Architecture:** the seam stays `bf-engine`. `bf-story`'s search, stats and auto-balance become generic over a
"fight one seed into a `Candidate`" function (`FightFn`). The current-engine entry points keep their signatures and
delegate, so their results are unchanged. `bf-engine` gains `Prepared`, a fight file made ready once, which turns a
seed (and a handicap) into a `Candidate` on the file's engine. The app's workers (`engine/search.rs`, `balance.rs`,
`takes.rs`, `jobs.rs`) and the CLI call `Prepared` and never `classic_setup` directly. The app keeps one engine
choice per draft (`Draft.engine`). The registry decides which fighters each engine offers. The preview draws
Engine 2 takes with `bf2-render` on eframe's own wgpu device (`bf2_render::Gpu::from_device`), through the
existing `FrameSource` trait, so `preview/scheduler.rs` and `preview/player.rs` stay as they are.

**Tech Stack:** Rust 2024, egui/eframe 0.37.0, wgpu 30.0.1, `bf-engine`, `bf-story`, `bf-content`,
`bf2-render`, `bf2-direct` (E4), `bf-export::job2` (E2, completed by E4/E5).

**Spec:** `docs/superpowers/specs/2026-11-17-engine2-design.md` section 6 (App integration), section 7 (test dummy
and fighter guide), section 8 row E6. It is done when the app is ready for fighter sessions.

## Global Constraints

- **Nothing breaks for current-engine fights.** A current-engine draft, search, balance, take, render job, history
  row and fight file behaves exactly as before. A fight file with `engine` absent is the current engine. A
  current-engine fight file the app writes still has no `engine` line. Every `bf-app/tests/ui` snapshot taken with
  no Engine 2 fighter offered is unchanged.
- **Both versions stay** (Aedan, 2026-11-17). A fighter with an Engine 2 version keeps `Engine::One` in
  `engines()`. Its current-engine version fights only current-engine matchups. Its Engine 2 version fights other
  Engine 2 fighters, the TEST DUMMY, or itself (a mirror).
- **No mixed-engine matchups.** A draft's two fighters always share the draft's engine (`pair_engines`).
- **The TEST DUMMY stays hidden** from Aedan's normal lists. It is offered only when the developer switch is on
  (ruling R2). It is never in `PORTED`/`available()`.
- **Interface:** no change beyond a small "Engine 2" mark where it helps (ruling R3). While no real fighter has an
  Engine 2 version and the developer switch is off, nothing on screen changes.
- Windows only. `bf-app` tests are Windows-only: in the cloud run `cargo check -p bf-app --all-targets`; the tests
  run on the PC through Remote Control (Task 9).
- Never edit `projects/`, `reelkit/`, `series/`. `git status --short projects reelkit series` is empty before every
  commit.
- Testing: only the changed parts (`bf-story`, `bf-engine`, `bf-content` registry and `fighters2`, `bf-cli` bins,
  the touched `bf-app` modules and their `tests/ui` files). Never the full suite.
- **No install in E6.** Versions, `tests/compat/` and the quick install check happen only if Aedan asks. Disk rules
  of `docs/studio/HANDOFF.md` "Disk space" apply, and `studio\scripts\clean-builds.ps1 -Apply` runs after merging.

## Rulings

- **R1 Engine choice.** `Draft` gains `engine: Engine` (`#[serde(default)]`, so `Engine::One`). A fighter is
  offered on an engine when `engines(name)` contains it. The matchup screen shows an engine switch only when an
  offered fighter has `Engine::Two`, so until F1 merges it shows nothing new. When the switch moves to Engine 2, a
  side without an Engine 2 version becomes the other side's fighter (a mirror match), with a notice that says so.
  When both sides lack one, the switch is not offered. Moving back to the current engine keeps both fighters if
  they have one, and otherwise starts the pair over from `START`.
- **R2 The developer switch.** The environment variable `BALLFIGHT_DEV=1`, read once at start-up into
  `EngineConfig.dev` and `ViewModel.dev`, adds the TEST DUMMY to Engine 2's lists. There is no switch on screen. The
  CLI (`ballfight search|balance|render|frame`) fights any Engine 2 file, with or without the variable. A TEST
  DUMMY file opened without the switch is refused in words ("TEST DUMMY is a developer fighter. Start the app
  with BALLFIGHT_DEV=1 to open it."), the way an unknown fighter is today.
- **R3 The mark.** One small chip, the text "Engine 2" in the theme's `small` style with the `FAINT` colour,
  appears in four places, and only for Engine 2 items: the matchup header, a render queue row, a Matchups row and
  the Library cover's caption line. Current-engine items get no mark, so their layout and snapshots are unchanged.
- **R4 Preview device and size.** The window's device is shared: `cc.wgpu_render_state` gives `Gpu::from_device`
  at start-up, kept as `Option<Arc<Gpu>>` in `Boot` and `EngineConfig.gpu`. Without one (the app is drawing
  without wgpu, or in a test), the take worker makes `Gpu::headless()` once, lazily. When that fails too, the take
  fails with "This PC's graphics card cannot draw Engine 2 fights." The preview renders at 540 x 960 (half of
  1080 x 1920, the same passes) and the preview texture uses `TextureOptions::LINEAR` for any frame other than
  360 x 640. Render jobs keep their own headless device (`run_job2` as E2 built it), so a lost device in a job
  never takes the window with it.
- **R5 One wgpu.** `bf2-render` and eframe must resolve to the same `wgpu` (30.0.1). Task 6 checks it with `cargo
  tree -p bf-app -i wgpu`, which must print exactly one version.
- **R6 History and caches.** `FightRecord` gains `engine: Engine` (`#[serde(default)]`). `History::record` treats
  the same pair and seed on another engine as another row. Shortlist caches are already apart, because
  `FightFile::search_key` appends `;engine=2`.
- **R7 Checks.** An Engine 2 job's step list holds only the lines whose checks are in `CHECKS2`. The flash line is
  never shown for Engine 2 (no flash cap).

## Review Focus

1. **Files from before E6.** A settings, queue, draft, history or shortlist file written by today's app loads
  unchanged as the current engine, and saving it again writes the same bytes (no `engine` key on current-engine
  rows). Pinned in Task 4 (`old_files_load_as_engine_one`, `engine_one_round_trips_byte_identical`).
2. **A mixed pair sneaking in.** Through a fighter pick, a swap, the engine switch, opening a file, a queued job or
  a Matchups row re-opened, the draft's two fighters must always both have the draft's engine. Pinned in Task 7
  (`no_action_sequence_makes_a_mixed_pair`, 2,000 random action sequences on the state machine).
3. **No shared device.** The window started without a wgpu render state, or on a software adapter: an Engine 2
  preview falls back to a headless device or fails the take in words, and never panics the interface thread.
  Pinned in Task 6 (`engine2_take_without_window_device_falls_back`).
4. **A frame that fails to draw.** A render error inside `Frames2::frame` must reach the scheduler as a failed
  frame (the source panics with a sentence, which the scheduler catches, as widget rule 11 says) and the next
  frame still draws. Pinned in Task 6 (`engine2_frame_failure_is_a_failed_frame`).
5. **The dummy leaking.** With `BALLFIGHT_DEV` unset, the TEST DUMMY must not appear in the roster, the pickers,
  the Matchups history's swatches or the theme scores, and a TEST DUMMY file is refused. Pinned in Task 3
  (`dummy_only_with_dev`) and Task 7 (`dummy_absent_without_dev`).
